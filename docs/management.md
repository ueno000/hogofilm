# 工程管理（マネージャー）運用手順

仕様シートの変更を GitHub の Issue と Project「development」に反映するための手順。マネージャー役のセッションがこの手順で動く。開発セッションが守るルールは [CLAUDE.md](../CLAUDE.md) にある。

## 管理する場所

| 場所 | 役割 | 正とする情報 |
|---|---|---|
| 企画管理シート（Google スプレッドシート「保護フィルム貼りゲーム 企画管理シート」） | 仕様の数値・パラメータ・配点・称号 | **何を作るか（数値）** |
| [docs/game-plan.md](game-plan.md) | ゲームのルール・流れ・受け入れ条件 | **何を作るか（ルール・文言）** |
| GitHub Issue（`ueno000/hogofilm`） | 作業の単位。仕様変更の履歴はコメントで残す | **作業内容と経緯** |
| GitHub Project「development」（https://github.com/users/ueno000/projects/1） | Status（Todo / In Progress / Done）と Track（Spec / Tech / Release） | **進捗** |

シートのタブの扱い:

| タブ | 種類 | マネージャーの扱い |
|---|---|---|
| 工程設計 / 調整パラメータ / 称号 | 仕様 | 読むだけ。**編集しない** |
| 進捗 | 管理 | Project の写しとして同期する（編集してよい） |
| プレイテスト記録 | 記録 | 読むだけ。気づいたことを Issue の材料にする |

## マネージャーの権限

- **してよい**: Issue の起票・コメント・ラベル付け、Project の Status / Track の更新、シートの管理部分（進捗タブ、Issue 番号欄）の編集、管理ドキュメント（`CLAUDE.md`、`docs/management.md`）の更新、コードの参照
- **しない**: `src/`・`tests/`・設定ファイルなど動くものの変更、シートの仕様部分の編集、開発セッションの作業ツリーやブランチの操作
- 管理ドキュメントの変更は、別の worktree で `docs/` ブランチを切り、`develop` 向けに PR を出す。マージはユーザーが判断する。

## 仕様変更が来たときの手順

ユーザーから「仕様が変わった」と連絡を受けたら、次の順に進める。

1. **シートを読む** — 仕様タブ（工程設計・調整パラメータ・称号）と、プレイテスト記録の新しい行を読む。
2. **コードと突き合わせる** — 調整パラメータの「現在値」と、コード中の同名の定数を比べる（ファイルは「ファイル」列に書いてある）。工程設計の配点は `src/game/score.ts` の `STAGE_WEIGHTS` と比べ、完了条件・品質・失敗時の扱いは各工程のロジックと比べる。
3. **ずれを Issue にする**
   - 既存の Issue の範囲内なら、その Issue にコメントで追記する（本文は書き換えない）。
   - 新しい作業になるなら、Issue を起票し、Project に追加する（Track=Spec、Status=Todo）。
   - 完了済みの Issue に関わる変更は、新しい Issue を起票し、元の Issue を `#番号` で参照する。
4. **Project を更新する** — Status と Track が正しいか確認する。
5. **進捗タブを同期する** — Project の Status をシートの進捗タブに写す（Todo=未着手、In Progress=進行中、Done=完了）。
6. **ユーザーに報告する** — 起票・コメントした Issue と、シート側で気になった点（入力ミスなど、仕様タブにある問題は直さずに報告する）。

### Issue コメントの書式

```markdown
## 仕様変更（シート: <タブ名> / <項目>）

- **変更内容**: <変更前> → <変更後>
- **理由**: <シートの変更メモ・プレイテスト結果・ユーザーの指示など>
- **影響範囲**: <関係するファイル・定数・工程・他の Issue>
```

## Track の使い分け

- `Spec` — シートや game-plan.md の仕様を実装する作業
- `Tech` — 基盤、描画、テスト、リファクタリングなど技術面の作業
- `Release` — 公開・配信の作業
